# Peek: план первой версии

Дата: 21 октября 2026 года.
Статус: начата реализация. Подготовлен Bun workspace с Next.js и выбранным экраном «Ночь» на демонстрационных событиях с живыми часами, приоритетами и жизненным циклом карточек. Бэкенд и интеграции ещё не реализованы.

## 1. Продукт и границы MVP

Peek — self-hosted веб-дешборд для постоянного отображения на втором мониторе, телевизоре, планшете или в отдельном окне браузера. Его задача — помочь с первого взгляда заметить событие, требующее внимания.

Основной принцип: пользователь настраивает приложение, после чего оно работает автоматически. Повседневное управление карточками, подтверждения, кнопки «Готово» и «Позже» не входят в MVP. Пустой экран — корректное состояние, если сейчас нет актуальных событий.

### В MVP входит

- Self-hosting через Docker Compose, без обязательного облачного аккаунта Peek.
- Один административный аккаунт на установку; несколько профилей людей и системный профиль «Общее».
- Несколько конфигураций экранов со своими URL, профилями и выбранными экземплярами сценариев.
- Общая адаптивная лента карточек с обозначением владельца, приоритетами и настройкой масштаба.
- Интеграция iCalendar: подписка на ICS по HTTPS URL, включая приватные URL подписок.
- Сценарий «Встречи»: предупреждения по календарным событиям.
- Сценарий «Дедлайны»: показ приближающихся календарных сроков, в том числе учебных.
- Переиспользование одного подключения несколькими сценариями.
- SDK и манифесты интеграций и сценариев; локальное подключение пакетов при сборке.
- Статусы подключения, свежести данных, фонового процесса и связи экрана с сервером.

### В MVP не входит

Магазин, загрузка исполняемого кода во время работы, сторонние недоверенные плагины, Telegram, IMAP, синхронизация телефона, отдельные аккаунты и права каждого участника, автоматизация присутствия, собственный визуальный редактор и произвольные компоненты карточек из расширений. Идеи и условия их внедрения перечислены в [future-ideas.md](future-ideas.md).

## 2. Техническая архитектура

### Стек

| Область | Решение |
| --- | --- |
| Веб-приложение | Next.js App Router, React, TypeScript |
| Интерфейс настроек | shadcn/ui, Tailwind CSS |
| Runtime и инструменты | Bun, Bun workspaces, Bun test |
| Фоновая обработка | Отдельный долгоживущий процесс Bun |
| Данные | SQLite на локальном диске, Drizzle ORM и миграции |
| Валидация границ | Zod; сериализуемые описания полей настроек |
| Обновления браузера | Server-Sent Events (SSE) и полный снимок состояния |
| Поставка | Docker Compose, образы web и worker из одного репозитория |

На старте реализации выбрать актуальные стабильные совместимые версии, проверить сборку и запуск Next.js под Bun и зафиксировать зависимости lockfile. Не использовать плавающие версии production-образов.

### Разделение ответственности

- **web:** авторизация, настройка профилей, экранов, подключений и сценариев; API и поток состояния экрана. Не запускает синхронизацию или расписания внутри HTTP-запросов.
- **worker:** синхронизация источников, обработка изменений, расписания сценариев, актуализация карточек, повторы после ошибок и heartbeat.
- **SQLite:** источник истины для конфигурации, нормализованных событий, заданий, карточек и статусов. Никакой обязательной зависимости от Redis или внешнего брокера.
- **Браузер:** отображение разрешённого состояния, локальный обратный отсчёт, переподключение и индикатор отсутствия связи. Секреты подключений браузеру не передаются.

Для MVP поддерживается ровно один экземпляр web и один worker на одном хосте. SQLite использует WAL, busy timeout и короткие транзакции. Файл БД находится на локальном persistent volume, не на сетевой файловой системе. Масштабирование на несколько хостов не входит в первую версию.

### Структура репозитория

```text
apps/
  web/
  worker/
packages/
  core/          # предметная модель, реестр и исполнение
  sdk/           # публичные контракты расширений
  db/            # схема, запросы и миграции
  ui/            # компоненты и стандартные карточки
extensions/
  integrations/
    ical/
  scenarios/
    meeting-alerts/
    calendar-deadlines/
docs/
```

SDK не зависит от Next.js или компонентов UI. Серверный код интеграций не импортируется в клиентский bundle.

## 3. Сущности и контракты расширений

### Основные сущности

| Сущность | Смысл |
| --- | --- |
| Integration definition | Пакет кода работы с источником, его manifest и предоставляемые возможности |
| Connection | Экземпляр интеграции: владелец, настройки, секреты и статус синхронизации |
| Scenario definition | Пакет бизнес-логики с manifest, зависимостями и описанием настроек |
| Scenario instance | Настроенный сценарий: владелец, параметры и привязки подключений |
| Card | Результат сценария с жизненным циклом и стабильным ключом |
| Profile | Метка владельца данных и карточек; в MVP не отдельный аккаунт авторизации |
| Screen | Именованная конфигурация отображения профилей и экземпляров сценариев |

Подключение и сценарий принадлежат одному профилю, включая «Общее». Администратор явно выбирает подключения для каждого сценария; автоматического доступа ко всем аккаунтам нет. Совместные сценарии могут использовать выбранные подключения разных профилей: это явное решение администратора, а не обход прав отдельных пользователей, которых в MVP ещё нет.

### Манифесты и зависимости

У интеграции: стабильный ID, версия пакета, версия API SDK, название, описание, предоставляемые возможности и описание настроек подключения.

У сценария: стабильный ID, версия, версия API SDK, название, описание, настройки, роли подключений и зависимости. Каждая роль объявляет требуемую возможность, обязательность и количество допустимых подключений. Для конкретных интеграций можно дополнительно объявить ограничение по ID и совместимой версии.

Сценарий может одновременно использовать разные интеграции, несколько подключений одной интеграции или работать без внешнего подключения. Никакой зависимости ядра от единственного календаря в коде сценариев быть не должно.

В MVP реализовать capability `calendar.events`. Встречи и дедлайны используют этот контракт, а не напрямую код iCalendar. Не создавать универсальный формат для событий, писем и сообщений.

Локальные пакеты обнаруживаются через отдельный реестр сборки. Добавление расширения требует добавления пакета, записи в реестре и пересборки, но не изменений логики ядра. Проверка реестра выявляет дублирующиеся ID, несовместимый SDK и отсутствующие или несовместимые зависимости.

Форма настройки создаётся из ограниченного набора описанных полей: текст, секрет, число, переключатель, выбор, список значений. Привязки подключений отображаются общим компонентом ядра. Сервер повторно валидирует входные данные.

### Исполнение

- Интеграция синхронизирует данные один раз на подключение независимо от количества потребителей.
- Сценарий получает только настройки и данные явно привязанных подключений через SDK; не получает секреты и доступ к БД через контракт.
- Обработчик сценария возвращает желаемое состояние своих карточек и время следующего запуска. Ядро выполняет upsert и удаление неактуальных карточек одной транзакцией.
- Повторный запуск с теми же данными не создаёт дубликаты.
- Сценарий запускается при изменении данных, настроек и наступлении сохранённого времени следующего запуска.
- Ошибка отдельной синхронизации или сценария фиксируется, не прерывая обычную обработку остальных. После аварии всего worker Docker перезапускает процесс, работа восстанавливается из БД.
- Локальные расширения доверенные. Интерфейс SDK не является sandbox: сторонний код нельзя считать изолированным только потому, что ему не передали секреты через аргументы.

### Карточки

Минимальные поля: стабильный ключ внутри экземпляра сценария, владелец, тип стандартного отображения, заголовок, пояснение, приоритет, `visibleFrom`, `expiresAt`, целевое время события и ссылки на источники данных для определения свежести.

В MVP достаточно стандартных карточек предупреждения и срока с обратным отсчётом. Сценарии управляют содержимым и приоритетом, ядро — расположением, размером и стилем. Текст источников отображается как текст, без исполнения HTML.

## 4. Поведение первой версии

### iCalendar

- Настройки: название, HTTPS URL подписки, профиль и интервал обновления; по умолчанию 60 секунд.
- URL подписки считается секретом: не выводится в логи и состояния экранов, шифруется при хранении.
- Использовать готовую библиотеку парсинга и раскрытия повторений; не писать собственный парсер RFC.
- Нормализовать UID, идентификатор повторения, заголовок, описание, начало, конец, часовой пояс, признак события на весь день и отмену.
- Поддержать повторения, исключения и перенос отдельных повторений, TZID и события на весь день. Для времени без TZID использовать часовой пояс подключения, по умолчанию часовой пояс установки.
- Раскрывать повторения в скользящем окне: от суток назад до 90 дней вперёд. Параметры сценариев не выходят за этот горизонт.
- Применять ETag/Last-Modified, если источник их предоставляет; таймаут запроса 15 секунд, ограничение ответа 10 MiB.
- Разрешать HTTPS на публичные адреса; отклонять loopback, private/link-local адреса, в том числе после DNS-разрешения и перенаправления. Поддержку локальных календарных серверов оставить отдельной будущей настройкой.
- После ошибки сохранять последние успешные данные с отметкой устаревания. Повторы с увеличением интервала до 15 минут; успешное обновление возвращает обычный интервал.
- Снимок событий заменяется только после успешного получения и разбора источника. Исчезнувшие или отменённые события перестают порождать карточки.

### Сценарий «Встречи»

- Принимает одно или несколько календарных подключений.
- Фильтр: все события либо регистронезависимое вхождение заданного текста в заголовок. По умолчанию — все события с конкретным временем; события на весь день исключены.
- По умолчанию карточка появляется за 10 минут; за 1 минуту становится срочной. Оба порога настраиваются, первый должен быть больше второго.
- После начала показывает, что встреча началась; исчезает через 5 минут после начала либо при окончании события, если оно раньше.
- Один экземпляр события имеет одну карточку на экземпляр сценария. Перенос обновляет время и расписание; отмена удаляет карточку.
- Сопоставление одинаковых встреч между разными календарными подключениями в MVP не выполняется.

### Сценарий «Дедлайны»

- Принимает одно или несколько календарных подключений.
- Настройка отбора: все события либо вхождение текста в заголовок; режим фильтра выбирается явно при настройке.
- Сроком считается начало события. Для события на весь день — конец указанного календарного дня в часовом поясе подключения, а не UTC-полночь.
- По умолчанию карточка появляется за 7 дней до срока, повышает приоритет за 24 часа и остаётся ещё 24 часа после срока с пометкой «Срок прошёл». Пороги настраиваются в пределах горизонта синхронизации.
- Истечение карточки не означает выполнение задания. У сценария нет статуса «сдано», если источник не предоставляет такую информацию.

### Профили и экраны

- Установка имеет часовой пояс; при первоначальной настройке предложить пояс браузера и дать изменить его. Временные метки хранить в UTC, календарные даты на весь день сохранять отдельно от временных меток.
- Профиль содержит имя и цветовой акцент. Имя всегда отображается текстом: одного цвета недостаточно для различения.
- Экран содержит название, выбранные профили, список экземпляров сценариев либо режим «все сценарии выбранных профилей», масштаб и часовой пояс отображения.
- В MVP одна смешанная лента. Карточки сортируются по приоритету, затем по целевому времени и стабильному ключу.
- При нехватке места самые важные карточки остаются первыми, отображается количество остальных; доступна обычная прокрутка. Автоматической карусели и скрывающей срочное ротации нет.
- Нейтральное пустое состояние и компактный статус системы. Без погоды, RSS и декоративных виджетов для заполнения пространства.
- Интерфейс не зависит от наведения мыши и работает в портретном и альбомном окне. Постоянного мигания нет, учитывается reduced motion.

### Доставка состояния и свежесть

- `GET /api/screens/:id/state` выдаёт разрешённый снимок карточек, статусов, серверного времени и монотонную ревизию состояния.
- `GET /api/screens/:id/events` открывает SSE и отправляет актуальный полный снимок при подключении и изменении ревизии. Для домашнего масштаба полный снимок проще дельт и предотвращает потерю изменений.
- Web проверяет ревизию БД раз в секунду общим циклом для подключённых клиентов; Redis и отдельный запрос к источнику на каждое подключение браузера не нужны.
- Карточки и ревизия обновляются в одной транзакции. Клиент не применяет более старую ревизию. SSE использует keepalive; документировать отключение proxy buffering.
- Браузер переподключается автоматически; разрыв отображается явно. Просроченные карточки скрываются по `expiresAt`, даже если соединение отсутствует.
- Показывать отдельно ошибки источников, время последнего успешного обновления, остановку worker и потерю связи с web.
- Worker пишет heartbeat каждые 5 секунд; отсутствие более 30 секунд означает проблему. Данные подключения считаются устаревшими после двух интервалов синхронизации плюс 30 секунд; ошибки показываются сразу.

## 5. Доступ, хранение и эксплуатация

- Первоначальная настройка защищена одноразовым bootstrap-секретом, заданным при развёртывании. Она создаёт администратора и после завершения блокируется.
- Администратор входит по паролю; сессия хранится в HttpOnly cookie. Изменяющие запросы проверяют авторизацию и Origin; попытки входа ограничиваются по частоте. Пароль хранится как стойкий хеш.
- Профили в MVP являются организацией данных, а не границей доступа между людьми. Настройки всех профилей доступны администратору; это явно указано в UI и документации.
- Для просмотра экран сопрягается одноразовым кодом с ограниченным временем действия и частотой попыток. Браузер получает отзывную сессию только для конкретного экрана. Обычный URL экрана не содержит постоянный секрет.
- Экранная сессия не может читать настройки подключений или менять конфигурацию. Администратор может отозвать сопряжение.
- Секреты подключений шифруются аутентифицированным шифрованием с отдельным ключом из окружения. Ключ не хранится в БД; при его отсутствии приложение с существующими данными завершается с понятной ошибкой.
- Docker Compose запускает отдельный одноразовый сервис миграций, затем web и worker. При ошибке миграций запуск зависимых сервисов прекращается.
- Web и worker используют общий volume данных, restart policy и проверки здоровья. Наружу публикуется только web. Для удалённого доступа документируется HTTPS reverse proxy.
- MVP содержит инструкции резервного копирования при остановленных web и worker: БД, необходимые сопутствующие файлы и отдельное сохранение ключа шифрования. Проверить восстановление на чистой установке.
- Логи содержат технические ошибки и идентификаторы, но не токены, URL подписок или содержимое личных событий.

## 6. Этапы реализации

### Этап 1 — каркас и воспроизводимый запуск

Создать workspace, Next.js, worker, общие пакеты, lint/typecheck/test команды и Docker Compose. Добавить схему БД, миграции, конфигурацию и heartbeat.

Готовность: чистая установка запускается одной командой, оба процесса видят БД, данные сохраняются после перезапуска контейнеров.

### Этап 2 — ядро расширений

Реализовать SDK, реестр, манифесты, проверку зависимостей, настройки, привязки подключений, исполнение сценариев, сохранённое расписание и жизненный цикл карточек. Добавить тестовые источники и часы для детерминированных проверок.

Готовность: локальный тестовый сценарий подключается без изменения логики ядра, повторные запуски не дублируют карточки, расписание переживает перезапуск. Контракт проверен сценарием с двумя разными тестовыми интеграциями и сценарием без интеграции.

### Этап 3 — доступ и настройка

Реализовать bootstrap, вход администратора, профили, подключения, формы сценариев, настройки экранов и сопряжение браузера.

Готовность: можно настроить два профиля и общий экран; экранная сессия не имеет доступа к административным операциям.

### Этап 4 — первая полезная цепочка

Реализовать iCalendar и «Встречи», подключить реальный календарь и проверить полный путь от источника до сохранённой карточки. Добавить «Дедлайны» через тот же SDK и то же подключение.

Готовность: оба сценария работают на одном синхронизируемом источнике; второй сценарий не потребовал изменений логики ядра.

### Этап 5 — постоянно открытый экран

Реализовать стандартные карточки, адаптивную ленту, профили, масштаб, SSE, восстановление соединения и все состояния свежести.

Готовность: изменение сохранённого состояния появляется на открытом экране за 2 секунды в локальной сети. Это не обещание скорости обнаружения внешних изменений: она зависит от интервала синхронизации.

### Этап 6 — проверка и документация

Выполнить тесты ниже, проверить производственную сборку и суточный прогон. Подготовить README по установке, обновлению, backup/restore и сопряжению экрана, а также руководство автора локального расширения.

Готовность: новый пользователь может развернуть Peek и подключить календарь по инструкции; автор расширения может добавить сценарий без изменения ядра.

## 7. Проверки и критерии приёмки

### Автоматические проверки

- Манифесты: отсутствующая зависимость, несовместимая версия, необязательная роль, несколько интеграций, несколько подключений и отсутствие подключений.
- Календарь: повторения, исключения, отмена, перенос, смена часового пояса, DST, события на весь день и ошибочный ICS.
- Встречи: точные границы обоих предупреждений, запуск приложения между порогами, раннее окончание, изменение события и отсутствие дубликатов.
- Дедлайны: календарный конец дня, повышение приоритета, просрочка и автоматическое исчезновение без ложного статуса выполнения.
- Исполнение: повтор задачи, восстановление после перезапуска, ошибка одного сценария, общее подключение для двух потребителей.
- SSE: первоначальное состояние, обновление, обрыв, переподключение, недопущение отката ревизии, истечение карточки без сети.
- Доступ: административные операции закрыты для экранной сессии, доступ ограничен выбранным экраном, отзыв сессии, защита bootstrap и отсутствие секретов в API.

### Сквозные и эксплуатационные проверки

- Настроить два личных профиля, «Общее», одно календарное подключение и два сценария; открыть разные конфигурации экрана в двух браузерах.
- Проверить читаемость и отсутствие горизонтального переполнения при 1920×1080, 1280×720, 768×1024 и узком окне 390×844. Настройки доступны с клавиатуры.
- Прервать доступ к календарю: старые данные обозначены, остальные сценарии продолжают работать. Остановить worker при работающем web: проблема видна на экране.
- Перезапустить контейнеры: подключения, конфигурация и актуальные карточки восстанавливаются без повторного ввода секретов.
- Восстановить backup на чистой установке с прежним ключом; проверить понятный отказ при неверном ключе.
- Суточный прогон с переподключениями: нет растущего числа подписок, дубликатов карточек и неограниченного накопления завершённых задач.
- Выполнить typecheck, lint, unit/integration tests и production build на зафиксированных версиях Bun и Next.js.

## 8. Принятые допущения

- MVP предназначен для одной домашней установки, один администратор настраивает её для всех участников.
- Пользователь управляет исходными событиями в календаре; Peek автоматически отражает изменения.
- Первые расширения поставляются вместе с приложением и считаются доверенными.
- Установка или изменение состава пакетов требует пересборки и перезапуска; включение и настройка уже доступных сценариев — нет.
- Смешанная лента — единственная компоновка MVP; split screen остаётся будущей возможностью.
- Первая реальная интеграция — iCalendar. Общность работы с разными интеграциями подтверждается контрактными тестами SDK, а не преждевременной реализацией Telegram или IMAP.
